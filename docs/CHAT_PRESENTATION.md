# Chat presentation

Tool transport messages are machine-readable, while the conversation should remain readable to a person. The injected runtime identifies setup, ready, call, result, and event frames and moves them into a collapsible execution-details panel.

The panel shows current task status, tool progress, recovery state, and items that need attention. It starts collapsed and uses accessible controls. A user discussing protocol text as ordinary prose does not cause that message to be hidden.

## DeepSeek chat page

The direct-API conversation is rendered by a bundled WebView page in `assets/chat` with a ChatGPT-style layout: a conversation drawer (search, date groups, delete), a top bar with the model name and a new-chat action, and a rounded composer whose send button becomes a stop button while a task runs. Text sent during a running task is delivered as guidance.

Assistant replies are rendered as Markdown with tables, task lists, KaTeX math (`$…$`, `$$…$$`, `\(…\)`, `\[…\]`), highlight.js code blocks with copy buttons and lazily loaded Mermaid diagrams. Raw HTML is disabled, Mermaid runs in strict mode, and a content-security policy blocks network access. Images are limited to `data:` URIs and image files from the workbench workspace (`![chart](workspace:out/chart.png)`), served by the activity with path checks.

Each turn groups the agent's work into one process card above the answer: a live line showing the current tool while running, then a collapsed "completed N steps" summary. Expanding it shows every tool call with its arguments, result or error, and progress notes. The page talks to `ApiChatActivity` through a small JavaScript interface; all other navigation opens in the system browser.

## Working state and message actions

While the AI works, the turn's process card is a full-width glass card that shows the current action, the step count, the elapsed time and the AI's latest note. The individual steps stay folded inside it. When the turn ends it shrinks to a "completed N steps · elapsed" capsule that can be opened.

Tapping one of your messages shows Copy, plus Edit and Delete on API platforms. Answers have Copy and, on API platforms, Delete. After a platform switch, older answers show which platform wrote them. On ChatGPT Web only Copy is offered, because the conversation's context belongs to chatgpt.com.

## ChatGPT web platform

**Older history and more chats come from the page.** The local page is a separate WebView that renders what the runtime reads from chatgpt.com's DOM. Pulling down at the top of the local thread calls `loadOlder()`: the runtime scrolls chatgpt.com's own thread container to its start so the site loads and renders older turns (it virtualizes long chats); they arrive with the next snapshots, and the local page keeps the reading position while turns are inserted above. Nothing is sent to ChatGPT. Reaching the end of the drawer list calls `moreConversations()`: the next page of `/backend-api/conversations` from the current count (or, without the API, the site's sidebar scrolled to its end); pages are merged, a first-page refresh never drops loaded pages, and the app's local cache keeps every listed chat. The list shows "loading" and "no more" notes.

**Detecting a reply in progress.** `generationActive()` combines page signals because the site's markup changes: the stop button (`data-testid="stop-button"`, any test id containing "stop", a stop label, or any stop control inside the composer form) and thinking/streaming indicators that follow the newest user turn in `main` (shimmer, streaming, `aria-busy`, thinking test ids), excluding the composer and the "connection interrupted" banner. The signal in use is `live.page_signal`; non-classic signals are traced as `page_generation_<signal>`. The site's own thinking line is shown as a page line while no reply text exists. A newest user turn with no reply at all is treated as idle only after 45 s (8 s otherwise).

**The page is the reference.** The runtime records when anything on chatgpt.com last changed. When the page shows no reply in progress, nothing changed for 8 s and OPhone AI is not writing to the page or running a tool, the page has *settled*: any bookkeeping that still says "busy" (a send just made, a result just delivered, an unanswered call) is treated as stale, the local page shows idle, and the next message goes out as a normal turn. A tool result that is still waiting on a settled page carries the user's message as `user_guidance` for one more delivery; if that also fails, the result is dropped and the message is sent as an ordinary turn. The setup notice covers only the composer (transparent blocker plus a small card above or below it), the delivery note is one line high, and masks or notes left by an interrupted write are removed on the next tick.

Since 1.10 the ChatGPT platform again shows OPhone AI's own chat page (`assets/chat`, `provider=web`) on top of chatgpt.com, which runs underneath with the injected runtime. 1.7 tried this and failed because typing into a page in the background needed input focus; the runtime now writes the editor without focus, so the local page works. The page reads the conversation from chatgpt.com (`snapshot()`), shows steps and answers like the API platforms, and sends typed messages through `submit()`, which queues them until the page is ready and the model is idle (guidance while a task runs). The site itself is one tap away (drawer: "ChatGPT page") with the slim bar below; the chat page's banner shows sign-in, verification, network and tool problems and the tool setup progress.

- Live detail: while ChatGPT works, the process card's subtitle and expanded body show OPhone AI's own stage and its duration (waiting for ChatGPT, planning the next action, writing the answer with its length, delivering a result) and the status lines chatgpt.com itself shows in the newest reply outside the answer, such as "Thought for 12s" or a reasoning summary (`liveInfo()`). Nothing beyond what the page shows to the user is read.
- Placement: while a turn is live its process card sits below the newest reply text; when the turn ends it moves back to the top of the turn as the "completed N steps" summary.
- Working state: the local view treats ChatGPT as working only while it generates, a tool runs or a result is being delivered, or for up to 30 s after a message or result was sent and before the reply starts (`modelWorking()`). An open native task alone does not count, so after ChatGPT stops the composer is idle again and a new message is sent as a normal message; guidance still waiting for a tool result is sent as a message once ChatGPT is idle.
- On-demand setup (`OPhoneAI.lazySetup`, set by the app): opening or browsing a conversation injects nothing and the tools show "standby". The handshake is sent only when the user sends a message. A conversation that was connected before (its setup and READY are on the page) is reused without a new handshake; one that never was gets one setup message first, and the user's message follows after ChatGPT confirms. A message sent on the page itself is held while connecting, then sent, so no text is lost. New chats no longer create empty "setup" conversations in the ChatGPT history. Nothing else starts a handshake: an old chat whose history loads slowly is not a setup failure while nothing waits to be sent, and a retry (automatic recovery or the user's) only re-arms setup when no message is queued, so the next handshake again goes out right before the user's next message. A recovery before setup queues no event to ChatGPT.
- Conversation list: chatgpt.com's list (`/backend-api/conversations`, with the page's device header), every conversation link found on the page, and a local record of each conversation used in OPhone AI (ID, title, last use) are merged, newest first, so the drawer is never empty when the site's list cannot be read. Failures are logged once as `chatgpt_conversation_list_failed` with the reason. Every conversation the page has ever listed is kept in the local record, so a later read that fails or returns fewer items cannot empty the drawer; reads happen at most every 15 s (showing the list no longer triggers a read loop). The site's list is requested with its own page size first, then with a larger page.
- Switching views: a "Web" button in the local view's header and a "Local view" button in the page's bar switch layers only; the page, its runtime, a running task and queued messages are the same underneath. The last choice is remembered; picture-in-picture always shows the local view.
- A slim native bar above the page holds the app menu, a status pill and a new-chat button. The pill is green when the tools are ready, blue while preparing or working, and red with the runtime's error code when something failed ("phone tools failed (send_button_not_ready) · tap to retry"). Tapping it reloads an unreachable page or restarts the tool handshake.
- The menu has new chat, update (when a release is available, with a dot on the menu button), browser, settings, about, feedback and switch platform.
- A main-frame load failure (for example `net::ERR_TIMED_OUT`) is shown in the pill and retried automatically after 5, 15 and 30 seconds.
- In the page, protocol frames stay folded behind the floating details pill, which names the running tool and step while a task runs. The composer gate shows the setup error code when the handshake fails.
- Deliveries are quiet: the runtime writes the composer without focusing it (ProseMirror reads paragraph changes made to its DOM; focus + `execCommand` is only a fallback), so the keyboard does not open. While a result is delivered the whole composer area is hidden at its current height and a single "Handing the result to ChatGPT…" line is shown in its place, so the conversation does not jump.
- Fewer round trips: the protocol lets the model request up to 6 independent tools in one message (`{"call_id":"…","calls":[{"tool":…,"arguments":…}]}`). They run in order, stop at the first failure or at `ask_user`, and all results return in one `tool: "batch"` envelope with `results[]`. Each call keeps its own journal scope (`<call_id>.<n>`).
- After a route change the runtime adopts a conversation whose messages stay unchanged (3 s when a new chat received its `/c/<id>`, 15 s otherwise) instead of failing with `conversation_dom_not_ready`.
- The status pill reports a stall only after 15 s without a supervision reply. Tapping it runs `userRetry()`, which gives automatic recovery a fresh budget before repairing.

The runtime also exposes `submit`, `userStop` and `snapshot` (used by tests and by the chat page's `provider=web` mode, which is currently not wired into an activity).

The fixture in `tests/chat-presentation.html` exercises presentation behavior against `ophone-ai-runtime.js` without invoking phone actions.

## Model and reasoning level (ChatGPT web)

The local view mirrors the ChatGPT page's own pickers. The runtime reads the model switcher's label and, when the current model has one, the reasoning-level picker beside the composer (`snapshot().model`). The chips above the input show both. Tapping one opens the same menu on the page, lists its choices (one submenu level, such as legacy models; switches such as temporary chat are skipped) and closes it again (`model_menu` in the snapshot). Choosing taps that item on the page, so the page stays the reference: the chip shows whatever label the page shows afterwards. Choosing is refused while ChatGPT is answering or a task runs.

## Formulas from the ChatGPT page

The chat view does not show the ChatGPT page's DOM. It rebuilds each answer from Markdown and renders it with its own markdown-it and KaTeX. For a formula, the runtime takes the TeX source from the page's KaTeX output (`annotation[encoding="application/x-tex"]`). Inline formulas are written as `\(…\)` and display formulas as `$$…$$`. A display formula met inside inline content (bold text, a list line, a table cell) is written as `\[…\]`. This avoids the `$…$` heuristics that reject `$n$1` or a closing `$` after a backslash.

A copy of the chat view's KaTeX build is loaded into the ChatGPT page as a private object (`window.__OPhoneAIKatex`, no global `katex`, no AMD registration). The runtime checks each formula with it. When it cannot render a formula the page shows, for example an extension such as `\ce{…}`, a site macro, or a formula without TeX source, the answer carries the page's rendered `.katex-html` for that formula (`item.math`, keyed by whitespace-normalized TeX). The chat view shows that markup after reducing it to KaTeX's spans and SVG strokes, with no scripts, images, event handlers or URLs. Other formulas are rendered locally, so snapshots stay small.

## ChatGPT web answers in their original Markdown

Once an answer is complete, the runtime reads the conversation through chatgpt.com's own conversation API (`GET /backend-api/conversation/{id}`). This is the signed-in user's own data, read from the same origin with the page's session, and it is kept on the phone and not sent anywhere else. Each assistant message's original Markdown is matched to the page message by its message id. The site's private-use citation markers are removed, since the page shows them as chips. The API is read again only when the page's answers change and nothing is being written; after a failure it waits 30 s. While an answer is still being written, or when the API cannot be read, the text reconstructed from the page (with page-rendered formulas as above) is used instead.

These answers (`raw: true`) are rendered by `vendor/web-markdown.min.js`, built in `tools/web-markdown` from open-source packages only: unified, remark-parse, remark-gfm, remark-math, remark-rehype, rehype-katex and rehype-stringify, with KaTeX 0.16.21, the same version chatgpt.com loads. The math rules follow chatgpt.com: `$$…$$`, `\(…\)` and `\[…\]` are math, while a single `$…$` is plain text (`singleDollarTextMath: false`). The `\(…\)` / `\[…\]` support is OPhone AI's own preprocessing, which skips code spans and fences. No code from chatgpt.com's scripts is used; they were only inspected to learn which public libraries and settings the site uses. Raw HTML in an answer is never rendered. Code blocks, tables, links (web and mail only) and images (data: or workspace only) then get this view's usual treatment.

API platforms keep this view's own rules: markdown-it, where `$…$` is also math, which DeepSeek and others use.

Rebuild the bundle with `cd tools/web-markdown && npm install && npm run build`. Versions are pinned in `package.json` and `package-lock.json`. The build also copies KaTeX into `vendor/katex` and writes `vendor/web-markdown.LICENSES.txt`.

## Drawer from either edge

On the chat pages (API platforms and the ChatGPT local view), a finger pulled in from the left or right screen edge drags the drawer out from that side, following the finger. On release it opens past 35%, or after a quick fling; otherwise it slides back. Back on a chat page never leaves it: it closes a sheet or the drawer, and otherwise opens the drawer. Switching platform is in the drawer.

The page gets the edge touches as follows (`EdgeDrawer`):
- **Android 10+:** a 200 dp band of each edge, a little below the middle, is excluded from the system back gesture (the most Android allows per edge).
- **Android 14+:** everywhere else on the edge, the system back gesture's progress and edge drive the same drag (predictive back, opted in for the two chat activities). Since the app compiles for API 33, the callback is reached by reflection.
- **Older versions and button navigation:** Back opens the drawer without following a finger.
